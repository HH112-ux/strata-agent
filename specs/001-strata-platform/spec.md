# Feature Specification：Strata 通用智能体平台

**Feature ID**: `001-strata-platform`
**Owner**: Caspian
**Status**: Draft
**Created**: 2026-11-13 | **Last Updated**: 2026-11-13
**Input**: 用户给定的平台定位、六层能力栈、9 个示例模块能力面、四个业务场景与六项创新能力（合计约 43–63 人日）
**Related**: `docs/adr/0001-six-layer-stack-and-docs-first.md`

## 1. 背景与问题（Context & Problem）

- **现状**：仓库尚无业务代码，只有能力范围与工程约束的约定；主线框架、存储与中间件选型尚未决策。
- **要解决的问题**：把"能调模型、能用工具、能单干也能协作、能编排工作流、出问题还能自己定位"从能力描述变成可运行、可验证、可演示的分层实现。
- **不做的后果**：能力停留在零散演示，无法证明工程完整度，四个业务场景也没有可复用的底座。
- **成功的样子**：六层中的任一层都能用一条命令启动并看到结果与运行轨迹，四个场景共用同一套底座。

## 2. 范围（Scope）

**In scope**

- [ ] 六层能力栈全部具备可运行实现：框架层、工具调用、单 Agent、多 Agent、Graph 工作流、运维可观测。
- [ ] 9 个示例模块，覆盖六层能力面对应的能力（模块清单与层级映射待确认，见 §9）。
- [ ] 四个业务场景：智能问答、合同预审、内容创作、数据分析。
- [ ] 六项创新能力：MCP 工具网关、可恢复 Graph 工作流、多 Agent 冲突裁决与共识、Agent 运行时可观测性、任务级评测与回归基线、持久记忆与高级 RAG。
- [ ] 工程基线：构建、测试、配置与密钥管理、CI 质量闸门。

**Out of scope**

- [ ] 商业化能力（计费、订阅、配额售卖）：本期无营收目标，引入会稀释能力栈建设。
- [ ] 独立前端控制台：本期通过 HTTP API 与命令行示例验证交互，不投入前端工程。
- [ ] 生产级高可用与集群编排：本期以本地可运行、单机容器可演示为准。
- [ ] 模型训练与微调：只做模型接入与调用编排。
- [ ] 移动端与小程序形态：与平台定位无关。

**边界与依赖**

- 上游依赖：模型服务经 provider 接口接入，默认对接火山方舟的 OpenAI 兼容端点（ADR-0003）；不可用时降级为桩模型，保证自动化测试与演示可跑。存储依赖 PostgreSQL + pgvector 与 Redis，由 Docker Compose 提供（ADR-0004）。
- 下游影响：四个业务场景与 9 个示例模块消费同一套平台接口；接口变更需同步更新场景侧调用。

## 3. 用户故事（User Stories，按优先级排序）

### US-1 — 分层底座与工具调用可运行（Priority: P1）

作为平台开发者，我希望框架层与工具调用层先具备可运行实现，以便所有上层 Agent 能力建立在可验证的底座上。

- **Why P1**：模型接入与受控工具执行是其余五层的共同前置，不先交付则后续全部空转。
- **Independent Test**：启动平台，提交一次需要调用白名单工具的任务，返回最终答案与 traceId；单命令可跑通该层自动化测试。
- **Acceptance Criteria（EARS）**

| ID | 场景/句式 | 期望结果 |
| --- | --- | --- |
| AC-1.1 | When 提交一次需要工具调用的任务，the 平台 shall 完成"模型调用 → 工具调用 → 结果回填 → 最终回答"的闭环 | 返回答案且轨迹中可见至少一次工具调用 |
| AC-1.2 | When 请求的工具不在白名单内，the 平台 shall 拒绝执行并返回明确的权限错误码 | 无外部进程被启动；错误码可被测试断言 |
| AC-1.3 | When 工具执行超过配置超时，the 平台 shall 中断执行并返回超时错误 | 执行时间不超过"超时阈值 + 容忍误差" |
| AC-1.4 | If 模型服务不可用，then the 平台 shall 切换到桩模型，保证自动化测试仍可完成 | 无真实 Key 时测试全绿 |
| AC-1.5 | When 一次运行发生模型或工具调用，the 平台 shall 记录结构化日志并携带 traceId | 日志可检索到该 traceId 的完整链路 |

### US-2 — 单 Agent 与多 Agent 协作（Priority: P1）

作为平台使用者，我希望单个 Agent 能独立完成任务，多个 Agent 能分工协作并在分歧时给出唯一结论。

- **Why P1**：单 Agent 是能力最小闭环；多 Agent 是平台"能协作"定位的直接体现，二者共用调度与消息模型。
- **Independent Test**：在 US-1 已交付的前提下，分别运行单 Agent 任务与双 Agent 协作任务，均可从轨迹看到分工、工具调用与最终结论。
- **Acceptance Criteria（EARS）**

| ID | 场景/句式 | 期望结果 |
| --- | --- | --- |
| AC-2.1 | When 提交一个可单 Agent 完成的任务，the Agent shall 自主决定步骤、调用工具并给出终止结论 | 轨迹包含任务分解与终止原因 |
| AC-2.2 | When 任务被分配给多个 Agent，the 平台 shall 按角色路由消息并记录各自产出 | 每个 Agent 的输入输出在轨迹中可区分 |
| AC-2.3 | When 多个 Agent 结论冲突，the 平台 shall 按既定裁决规则输出唯一结论并记录裁决理由 | 最终结果唯一；裁决记录包含各方意见与判据 |
| AC-2.4 | If 某 Agent 超时或失败，then the 平台 shall 降级完成任务或将任务标记为待人工，不得整体静默失败 | 任务状态为完成或待人工，且原因可查 |

### US-3 — 可恢复 Graph 工作流（Priority: P2）

作为工作流编排者，我希望流程能暂停等待人工、从检查点恢复，并在结果不合格时回退重跑。

- **Why P2**：工作流是长任务与人工介入的载体，依赖单/多 Agent 已就绪。
- **Independent Test**：在 US-2 已交付的前提下，运行一个包含人工介入节点与条件分支的工作流，暂停后恢复并完成。
- **Acceptance Criteria（EARS）**

| ID | 场景/句式 | 期望结果 |
| --- | --- | --- |
| AC-3.1 | When 提交工作流定义并执行，the 引擎 shall 按节点顺序与条件分支推进 | 轨迹可见实际经过的节点与分支判定 |
| AC-3.2 | When 到达人工介入节点，the 工作流 shall 暂停并等待人工提交后继续 | 暂停状态可查询；提交后从该节点继续 |
| AC-3.3 | When 从检查点恢复，the 工作流 shall 从最近检查点继续且不重复已提交的副作用 | 恢复后副作用次数与中断前一致 |
| AC-3.4 | When 某节点结果被判定不合格，the 工作流 shall 回退到指定节点并携带修正信息重跑 | 重跑记录包含回退目标与修正理由 |

### US-4 — MCP 工具网关（Priority: P2）

作为平台运维者，我希望外部 MCP 工具经统一网关接入，具备权限、审计、限流与沙箱四项约束。

- **Why P2**：工具暴露面扩大后，安全与可追溯是上线前提。
- **Independent Test**：注册一个 MCP 工具，分别以有权限、无权限、超限流三种身份调用，行为符合预期且审计可查。
- **Acceptance Criteria（EARS）**

| ID | 场景/句式 | 期望结果 |
| --- | --- | --- |
| AC-4.1 | When 已注册的 MCP 工具被有权限的调用方请求，the 网关 shall 完成调用并返回结果 | 调用成功且结果与工具声明一致 |
| AC-4.2 | When 调用方无该工具权限，the 网关 shall 拒绝调用并写入审计 | 返回权限错误码；审计记录包含调用方与工具名 |
| AC-4.3 | When 调用超过限流阈值，the 网关 shall 拒绝并返回可重试提示 | 超出部分全部被拒；提示含重试语义 |
| AC-4.4 | When 一次 MCP 工具调用结束，the 网关 shall 记录调用方、工具、参数摘要、结果状态与耗时 | 审计记录字段齐全且可查询 |

### US-5 — 运行时可观测与评测基线（Priority: P2）

作为维护者，我希望每一次运行都能被追踪、度量与回归对比，问题能自己定位到具体环节。

- **Why P2**：可观测与评测是把"能跑"变成"可持续维护"的分水岭。
- **Independent Test**：运行一次任务后按 traceId 查全链路；对固定评测集跑两次并得到基线对比报告。
- **Acceptance Criteria（EARS）**

| ID | 场景/句式 | 期望结果 |
| --- | --- | --- |
| AC-5.1 | When 任意任务运行结束，the 平台 shall 提供可按 traceId 查询的模型、工具与节点链路 | 链路节点完整、时序正确 |
| AC-5.2 | When 查询任务级指标，the 平台 shall 返回耗时、token、成本与状态 | 指标可按任务与 Agent 维度拆分 |
| AC-5.3 | When Agent 心跳超过阈值未更新，the 平台 shall 标记为疑似假死并触发处置记录 | 假死状态与处置结果可查 |
| AC-5.4 | When 对固定评测集执行评测，the 平台 shall 产出与上一基线的对比报告 | 报告含通过率、耗时、成本与退化项 |

### US-6 — 持久记忆与高级 RAG（Priority: P3）

作为平台使用者，我希望 Agent 能跨会话记住信息，并在回答中给出可核查的出处。

- **Why P3**：记忆与检索提升效果，但不阻塞平台主干能力交付。
- **Independent Test**：在一次会话写入偏好，另起会话召回；针对知识库提问时回答带出处。
- **Acceptance Criteria（EARS）**

| ID | 场景/句式 | 期望结果 |
| --- | --- | --- |
| AC-6.1 | When 会话中写入可持久化的记忆条目，the 平台 shall 在后续会话中按相关度召回 | 召回结果包含该条目且排序合理 |
| AC-6.2 | When 基于知识库回答，the 回答 shall 标注引用片段与来源 | 每个引用可定位到原始片段 |
| AC-6.3 | If 检索无相关命中，then the 回答 shall 明确说明依据不足，不得编造来源 | 无伪造引用；提示依据不足 |

### US-7 — 四个业务场景端到端（Priority: P2）

作为验收者，我希望四个业务场景都能在同一底座上端到端跑通，证明能力可复用。

- **Why P2**：场景是能力栈的落地证明，需在主干能力就绪后交付。
- **Independent Test**：在 US-1 至 US-5 已交付的前提下，分别运行四个场景的演示脚本，均产出可判定的结果。
- **Acceptance Criteria（EARS）**

| ID | 场景/句式 | 期望结果 |
| --- | --- | --- |
| AC-7.1 | When 使用智能问答场景发起多轮提问，the 场景 shall 给出回答并在需要时给出引用 | 多轮上下文保持；引用可定位 |
| AC-7.2 | When 提交一份合同样例，the 场景 shall 输出条款风险清单及对应依据段落 | 每条风险关联原文段落 |
| AC-7.3 | When 提交创作主题与大纲要求，the 场景 shall 产出结构完整的可编辑稿件 | 稿件结构符合大纲；无越界内容 |
| AC-7.4 | When 对样例数据集提问，the 场景 shall 给出结论与计算依据 | 结论可复算；依据可追溯 |
| AC-7.5 | When 四个场景运行，they shall 复用平台统一的模型、工具与可观测链路，不得自带旁路 | 场景代码中无独立模型客户端直连 |

## 4. 功能需求（Functional Requirements）

- **FR-1**：The system MUST 支持至少一种模型接入方式，并可通过配置切换模型与参数；主线为 Spring AI，LangChain4j 仅作模型接入层对照实现（ADR-0002）。
  - 追溯：AC-1.1, AC-1.4
- **FR-2**：The system MUST 通过统一工具注册表声明工具名称、参数、权限、超时与执行方式。
  - 追溯：AC-1.2, AC-1.3
- **FR-3**：The system MUST NOT 允许工具执行任意 shell 命令；白名单以外的调用一律拒绝。
  - 追溯：AC-1.2
- **FR-4**：The system MUST 为单 Agent 提供任务分解、工具选择、结果观察与终止判定能力。
  - 追溯：AC-2.1
- **FR-5**：The system MUST 支持多 Agent 的角色定义、消息路由、冲突裁决与共识输出。
  - 追溯：AC-2.2, AC-2.3
- **FR-6**：The system MUST 支持 Graph 工作流的节点、边、条件分支、检查点、人工介入与修正回退。
  - 追溯：AC-3.1, AC-3.2, AC-3.4
- **FR-7**：The system MUST 支持从检查点恢复工作流，且不重复已提交的副作用。
  - 追溯：AC-3.3
- **FR-8**：The system MUST 为 MCP 工具提供权限、审计、限流与沙箱四项网关能力。
  - 追溯：AC-4.1, AC-4.2, AC-4.3, AC-4.4
- **FR-9**：The system MUST 为每次运行生成 traceId，并贯穿模型调用、工具调用与工作流节点。
  - 追溯：AC-1.5, AC-5.1
- **FR-10**：The system MUST 提供任务级指标：耗时、token、成本、状态与心跳。
  - 追溯：AC-5.2, AC-5.3
- **FR-11**：The system MUST 提供任务级评测能力与可对比的回归基线。
  - 追溯：AC-5.4
- **FR-12**：The system MUST 提供跨会话持久记忆，以及回答可追溯到原文的 RAG 能力。
  - 追溯：AC-6.1, AC-6.2, AC-6.3
- **FR-13**：The system MUST 让四个业务场景复用同一套底座，不得出现场景私有的模型调用旁路。
  - 追溯：AC-7.5
- **FR-14**：The system MUST 提供 9 个示例模块，共同覆盖六层能力面（清单与映射待确认）。
  - 追溯：AC-1.1, AC-2.1, AC-3.1, AC-5.1, AC-6.2
- **FR-15**：The system MUST NOT 在仓库中存储任何真实凭据、私钥或带凭据的连接串。
  - 追溯：NFR-3
- **FR-16**：The system MUST 通过环境变量注入外部依赖配置，仓库仅保留占位样例。
  - 追溯：NFR-3
- **FR-17**：The system MUST 在无真实模型 Key 的情况下跑通全部自动化测试与演示脚本。
  - 追溯：AC-1.4, NFR-6
- **FR-18**：The system MUST 对公开类、接口、方法提供英文 Javadoc 并标注 `@author Caspian`，注释与日志文案不得使用中文。
  - 追溯：NFR-7

## 5. 非功能需求（Non-Functional Requirements）

- **NFR-1（性能）**：编排与工具调度的额外开销 p95 < 500ms；端到端问答 p95 < 8s（暂定基线，选型决策后按实测校准）。
- **NFR-2（可用性）**：模型服务不可用时降级为桩模型，测试与演示链路不中断。
- **NFR-3（安全/隐私）**：密钥零入库；工具默认拒绝；日志对密钥、完整提示词与个人敏感字段做脱敏。
- **NFR-4（可观测性）**：核心链路必须有 traceId、任务级指标与错误码；错误码按域前缀划分（模型、工具、工作流、权限、评测）。
- **NFR-5（兼容性）**：示例模块与业务场景共用平台接口；接口变更必须同步更新所有消费方并在 PR 说明。
- **NFR-6（可复现性）**：一条命令完成编译、单元测试与集成测试，不依赖真实付费 Key 与外部网络。
- **NFR-7（代码规范）**：公开 API 英文 Javadoc 齐全且标注 `@author Caspian`；代码注释与日志仅用英文；中文只出现在文档中。
- **NFR-8（可维护性）**：单个 PR 变更不超过 400 行；超出必须先报告并说明拆分方案。
- **NFR-9（可配置）**：所有外部依赖配置（模型 `base-url`、`model`、`api-key`，数据库与 Redis 连接串）MUST 通过环境变量注入；代码与配置文件中不得出现硬编码连接串、密钥与绝对路径。验收方式：启动校验测试覆盖"缺失必填变量即失败"；CI 扫描硬编码连接串、`jdbc:`、`redis://` 与绝对路径；`.env.example` 字段与代码读取项一一对应。
- **NFR-10（可测试）**：MUST 采用分层测试策略——单元测试覆盖核心分支（真实模型替换为桩 provider），集成测试使用 Compose 提供的 PostgreSQL 与 Redis，端到端测试覆盖四个业务场景；核心模块行覆盖率 MUST ≥ 70%，其余模块与示例/场景 MUST ≥ 60%，低于门槛 CI 失败。验收方式：CI 覆盖率报告与门槛配置可见；无真实 Key 时全量测试通过。
- **NFR-11（可观测）**：每次运行 MUST 产出 traceId 贯穿的结构化日志，并暴露任务级指标（任务总数、耗时、token、成本、工具调用次数、心跳缺失次数）；指标口径遵循 Spring Boot Actuator/Micrometer。验收方式：一次运行后可按 traceId 查到日志链路与对应指标，字段齐全。
- **NFR-12（一键启动）**：在仅安装 Docker 的机器上，`docker compose up -d --wait` MUST 启动 PostgreSQL、Redis 与应用并全部健康；随后一条命令跑通一次"模型调用 + 工具调用"链路。验收方式：干净环境按 `docs/quickstart.md` 执行一次，健康检查返回 UP 且冒烟脚本退出码为 0。

## 6. 关键实体与数据（Key Entities）

- **会话（Session）**：一次连续交互的上下文容器，关联多条消息与记忆条目。
- **任务（Task）**：一次可独立追踪的执行单元，关联 traceId、状态、耗时与成本。
- **模型调用记录（Model Call）**：一次模型请求的事实记录，含模型标识、token 用量、耗时与状态。
- **工具调用记录（Tool Invocation）**：一次工具执行的事实记录，含工具名、参数摘要、结果状态与耗时。
- **Agent 角色（Agent Role）**：协作场景中的职责定义与可用工具集合。
- **工作流定义与实例（Workflow Definition / Instance）**：定义描述节点与边；实例描述一次运行状态。
- **检查点（Checkpoint）**：工作流在某一节点后的可恢复快照，用于暂停、恢复与回退。
- **记忆条目（Memory Entry）**：跨会话保留的事实或偏好，带作用域与更新时间。
- **知识片段与引用（Chunk / Citation）**：检索单元及其在回答中的出处。
- **评测集与基线（Eval Set / Baseline）**：固定样本集合与一次评测的基准结果。

## 7. 边界与异常场景（Edge Cases）

- [ ] 模型超时或限流：按重试上限退避，超过后返回明确错误并降级到桩模型（测试场景）。
- [ ] 工具执行失败：将失败结果回填给 Agent，由 Agent 决定重试或改走其他工具，禁止静默吞错。
- [ ] 工具循环调用：达到最大步数或重复调用阈值即强制终止，并标记原因。
- [ ] 上下文超长：按策略裁剪并记录裁剪动作，不得直接报错终止。
- [ ] 人工介入超时：工作流保持暂停状态并记录等待时长，不自动跳过。
- [ ] 检查点恢复时副作用已执行：以幂等键判定，重复副作用不得发生。
- [ ] 无权限或未认证调用：返回统一权限错误码，不泄露工具是否存在。
- [ ] 成本或 token 超限：触发熔断，返回任务终止原因与已用成本。
- [ ] 空数据集或空知识库：明确返回"依据不足"，不得生成虚构结论。
