# ADR-0001：按六层能力栈分层建设并坚持文档先行

- **Status**: Accepted
- **Date**: 2026-11-13
- **Deciders**: Caspian
- **Related**: `specs/001-strata-platform/spec.md`、`specs/001-strata-platform/plan.md`

## 背景（Context）

平台从零开始，能力范围横跨模型接入、工具调用、单 Agent、多 Agent、Graph 工作流、运行时可观测，并叠加六项创新能力与四个业务场景。团队为单人开发，缺少同伴评审，必须用文档与自动化证据替代口头约定；同时需要一种能按层验收、能逐层证明可运行的推进方式，避免出现"骨架齐全但无行为"的空转。总工作量约 43–63 人日，要求每个阶段结束都有可演示的产出。

## 决策（Decision）

我们采用六层能力栈（框架层 → 工具调用 → 单 Agent → 多 Agent → Graph 工作流 → 运维可观测）作为仓库分层与交付顺序，并坚持文档先行：任何能力面在写实现前必须先完成 `spec.md`、`plan.md`、`tasks.md`，每层以"可运行命令 + 自动化测试 + 结构化运行轨迹"作为完成判据。

## 备选方案（Alternatives Considered）

| 方案 | 优点 | 缺点 | 为什么未选 |
| --- | --- | --- | --- |
| A（选中）按六层能力栈分层，文档先行 | 层间依赖单向、可逐层验收；每层可独立认领与演示；问题定位范围收敛 | 前期文档成本高；需要维护层间接口约定 | — |
| B 按业务场景切分（问答、合同、创作、分析各一套） | 场景交付直观，用户可感知快 | 同一能力重复实现，平台主线无法沉淀；场景间无法互相验证 | 与"通用智能体平台"定位冲突，创新项无处安放 |
| C 按传统 controller/service/dao 分层 | 开发习惯熟悉，上手快 | 无法表达 Agent、工具、工作流的能力边界；可观测与评测缺位 | 架构分层与能力分层错位，验收口径无法落到能力面 |
| D 先做场景，再补底座 | 早期有可见成果 | 底座返工概率高，场景间一致性差 | 会在 43–63 人日区间内造成重复投入 |

## 后果（Consequences）

**正面**

- 每层有独立验收口径，进度可量化，避免"整体完成度"含糊。
- 创新能力各自嵌入明确层级，减少跨层耦合。
- 文档先行使单人开发也能保持决策可追溯，后续对外展示有完整依据。

**负面 / 代价**

- 文档与一致性核对占用前期时间，短期看不到代码产出。
- 层间接口一旦调整，需要同步更新多份文档与任务。

**需要跟进的动作**

- [ ] 确认 9 个示例模块清单与六层映射，回填 spec（Caspian，tasks T007）
- [ ] 每条新能力开始前补齐 spec/plan/tasks 并通过 G1、G2（Caspian，持续）
- [ ] 每层交付时附可运行命令与测试证据（Caspian，持续）

## 合规性（Compliance）

- 与 `constitution.md` 的关系：符合 Article I（文档先行）、Article II（每层必须有可运行证据与测试）、Article VI（复杂度留痕）。
- 如何验证执行：PR 检查 spec/plan/tasks 是否存在且通过 G1、G2；每层 PR 必须附运行命令与测试结果；`docs/quickstart.md` 按层给出验证步骤。
