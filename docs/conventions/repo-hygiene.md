# 仓库卫生与提交边界

本文件回答一个问题：**什么能提交到 GitHub，什么绝对不能。** 每条给出判定理由与违反后果，可按第 6 节命令自检。
适用范围：`strata-agent` 的所有分支与所有提交者，包括 AI Agent。

## 1. 必须提交

决定项目能否复现的东西。缺失时不是“少个文件”，而是别人拿到的不是同一个项目。

| 内容 | 判定理由 | 不提交的后果 |
| --- | --- | --- |
| 依赖 lock 文件（`pom.xml`、`gradle.lockfile`、`package-lock.json`、`pnpm-lock.yaml`） | 锁定可复现的依赖图 | 每人解析出的版本不同，“我这里能跑”无法复现；线上与本地行为漂移 |
| 数据库迁移脚本（`db/migration/**`、`V*.sql`） | schema 是部署契约的一部分 | 新环境建不出库；手工改库导致环境间结构不一致，且无法回滚 |
| 构建脚本（`pom.xml`、`build.gradle(.kts)`、`settings.gradle`、`Dockerfile`、`docker-compose.yml`、`Makefile`） | 构建方式是代码的一部分 | 镜像与本地环境不一致，部署结果不可重复 |
| CI 配置（`.github/workflows/**`） | 质量门禁必须版本化 | 门禁只存在于某人机器上，无法审计，改坏无人察觉 |
| 规范与 spec（`AGENTS.md`、`docs/conventions/**`、`specs/**`、`docs/adr/**`） | 规格是行为事实源 | 实现失去验收依据，后续变更无法判断是否破坏契约 |
| 必要的样例数据（`data/fixtures/**`、`examples/**/resources/**`） | 测试与示例需要稳定输入 | 测试无法在干净环境跑通；示例对新人不成立 |
| 配置模板（`.env.example`、`application-example.yml`） | 只含占位符，说明需要哪些变量 | 新人不知道要配什么，只能逐个猜 |

判定口径：**换一台干净机器 clone 后能否构建、迁移、测试、运行？** 缺一项就说明有该提交而未提交的内容。

## 2. 绝不能提交

### 2.1 密钥与凭证

| 内容 | 泄露后的实际后果 | 撤销方式 |
| --- | --- | --- |
| `.env`、`.env.*`（含真实值） | 拿到文件即可调用付费模型与云资源，产生账单与数据外泄 | 立即在 provider 控制台轮换 key 并吊销旧 key；检查调用日志确认是否被滥用 |
| `*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.jks`、`*.keystore` | 可伪造服务端身份或解密历史流量；私钥泄露等于身份被接管 | 重新签发证书、吊销旧证书（CRL/OCSP）、更换 keystore 口令 |
| 云厂商 AK/SK（明文或写死默认值） | 可创建/删除资源、读取对象存储、横向提权，常见结果是挖矿与数据删除 | 在 IAM 禁用该 AK 并新建；审计 CloudTrail/操作日志；评估账单异常 |
| JWT 私钥、签名 secret | 可为任意用户伪造合法 token，绕过全部鉴权 | 轮换签名密钥使全部已签发 token 失效；强制重新登录 |
| 数据库连接串带密码 | 直连生产库读写，等价于数据库失守 | 改数据库口令；收敛来源 IP 与账号权限；核查慢查询与异常导出 |
| 第三方 API token、Webhook secret、Cookie/Session | 可代替持有者操作，常被用于投递垃圾或窃取数据 | 在对应平台 revoke 并重建；检查最近调用记录 |

**处理顺序**：先轮换或吊销，再处理仓库。历史改写不是首选——推送过的对象可能已被 fork、缓存或抓取，**轮换才是止损**。仅当凭证从未离开本机、且确认未被任何远端持有，才考虑清理历史。

### 2.2 真实用户数据与导出

| 内容 | 泄露后的实际后果 | 撤销方式 |
| --- | --- | --- |
| 含 PII 的数据库 dump（手机号、身份证、地址、订单） | 个人信息泄露，触发合规责任与通知义务；公开仓库等于永久公开 | 无法“收回”，只能删除仓库内容并评估是否需要依法告知；记录事件 |
| 真实业务 Excel / CSV 导出 | 同上，且常被忽略，因为“只是数据文件” | 从当前提交移除并轮换相关访问权限；评估影响范围 |
| 日志中夹带手机号、身份证、token | 日志通常体积大、评审跳过，泄露后难以逐条排查 | 删除文件；排查日志采集链路是否还有其他副本 |

替代做法：结构用 schema 或合成数据表达；需要真实分布时，脱敏后放 `data/fixtures/` 并在同目录 README 标注来源、脱敏方式与批准人（见第 3 节）。

### 2.3 模型权重与大文件

| 内容 | 泄露后的实际后果 | 撤销方式 |
| --- | --- | --- |
| 模型权重（`*.safetensors`、`*.gguf`、`*.onnx`、`*.pt`、`*.pth`） | 仓库体积膨胀、clone 与 CI 变慢；若权重受限则构成许可违约 | 从当前提交移除；改用对象存储或模型仓库并记录版本号；历史清理需全员重新 clone |
| 数据集、视频、压缩包等单文件 > 5MB | 同上，且 GitHub 对单文件与仓库体积有硬限制 | 用 Git LFS 或外部存储；在 README 写清获取方式与校验和 |

判定：**能用下载地址 + 校验和替代的，就不入库。** 确需入库的走第 3 节评审。

### 2.4 构建产物与依赖目录

`target/`、`build/`、`out/`、`node_modules/`、`.gradle/`、`*.class`、`*.jar`（wrapper 除外）。

后果：产物与源码不一致，评审看到的是二进制噪声；仓库随时间不可控地膨胀；可能把本地路径、编译期注入的配置打进 jar。
撤销：`git rm -r --cached <path>`，加入 `.gitignore` 后提交；无需改写历史，除非产物中含密钥（此时按 2.1 处理）。

### 2.5 本地环境与 IDE 配置

`.idea/`、`*.iml`、`.vscode/`、`.classpath`、`.project`、`.DS_Store`、`*.code-workspace`。

后果：他人的绝对路径、本地 SDK 名、个人调试配置进入仓库，引发无意义冲突；有时夹带数据库口令或代理地址。
撤销：`git rm --cached` 并加入 `.gitignore`；共享配置改为提交 `.vscode/extensions.json` 这类纯建议文件。

### 2.6 带 token 的截图与调试集合

Postman/Insomnia 集合、curl 脚本、浏览器截图里的 `Authorization: Bearer ...`、控制台打印的完整请求。

后果：图片不会被文本扫描命中，评审也常跳过，泄露后极难发现；token 往往权限过高。
撤销：按 2.1 轮换 token；删除图片并清理附件缓存；导出集合前用环境变量替换所有凭证。

## 3. 先评审再提交

不禁止，但必须先说明并在 PR 正文留痕。

| 对象 | 必须先回答的问题 | 通过标准 |
| --- | --- | --- |
| 测试固定数据 | 是否含真实用户信息？来源是什么？ | 全部为合成或已脱敏；同目录 README 写明来源、脱敏方式、批准人 |
| 大体积样例与 fixture | 单文件多大？仓库总增量多少？ | 单文件 ≤ 5MB、单 PR 增量 ≤ 20MB；超限改用外部存储 + 校验和 |
| 外部来源代码与片段 | 许可证是什么？是否允许商用与再分发？ | 许可证兼容并保留版权头；在 `docs/adr/` 或 `NOTICE` 记录来源与许可证；许可不明一律不用 |
| 从生产脱敏导出的数据 | 脱敏规则是什么？能否反推个体？ | 去除或泛化直接标识符；抽样验证不可反推；批准人书面同意 |
| 与业务无关的大重构 | 是否阻塞当前 feature？能否独立 PR？ | 单独 PR、行为不变、现有测试一行不改且全绿 |

未通过评审就提交，按第 2 节同等处理，并在 PR 中标注 `hygiene-exception` 及批准人。

## 4. 本仓库 `.gitignore` 基线

仓库根目录的 [`.gitignore`](../../.gitignore) 已按当前技术栈（JVM + Maven/Gradle、Spring Boot、PostgreSQL + pgvector、Redis、Docker Compose、模型接入）配置，覆盖四类：构建产物、IDE/OS、密钥与本机配置、运行时数据与模型文件。

它只防误添加，**不构成门禁**：`git add -f` 可以绕过，已跟踪的文件不受新增规则影响。真正的门禁是第 5 节的扫描，加上第 6 节的自检。

维护规则：

- 新增技术栈时同步补规则，并在 PR 中说明忽略的是什么、为什么可以忽略。
- 需要提交的目录若被规则误伤，用 `!` 白名单精确放行，例如 `!data/fixtures/**`，不要删掉整条规则。
- 已跟踪文件要停止跟踪，用 `git rm --cached <path>`，不能只改 `.gitignore`。

## 5. 密钥扫描：现状与最小接入

**现状（2026-11-13）**：本仓库没有 `.github/`、没有 `.pre-commit-config.yaml`、没有 `gitleaks.toml`，也没有任何提交钩子或 CI 扫描。当前唯一防线是人工评审。

**最小可行接入**，分两步，先本地后 CI：

1. 本地提交前扫描（拦截在推送之前）

   ```bash
   brew install gitleaks
   gitleaks protect --staged --redact --verbose
   ```

   通过后再 `git commit`。这是唯一能在密钥离开本机前拦住的环节。

2. CI 兜底（防绕过钩子与 `--no-verify`）

   新增 `.github/workflows/secret-scan.yml`，在 `push` 与 `pull_request` 上运行 gitleaks 官方 action，全历史扫描；命中即失败，且不打印明文。

   只有确认第 1 步与第 2 步都生效后，才可以把“已启用密钥扫描”写进交付报告。

**本次不修改 CI**：仓库当前没有构建与 CI，加扫描工作流会与 S1 阶段的门禁一起设计。接入前，密钥类问题一律按第 2.1 节人工核查。

扫描命中时的处理：

1. 停止提交，不回显明文，只报告文件、行号范围与凭证类型。
2. 判定是真实凭证还是测试占位符；真实凭证立即轮换（2.1）。
3. 确认是误报后，才在 `gitleaks.toml` 添加精确的 `allowlist` 条目，禁止整目录放行。

## 6. 提交前自检

```bash
# 1. 列出将要提交的文件，确认没有意外项
git diff --cached --name-only

# 2. 确认敏感路径确实被忽略（有输出即命中规则）
git check-ignore -v .env data/local/app.db models/weights.bin

# 3. 扫描暂存区凭证（接入 gitleaks 后）
gitleaks protect --staged --redact

# 4. 找出暂存区里的大文件（> 5MB）
git diff --cached --name-only -z | xargs -0 -I{} sh -c 'test -f "{}" && du -k "{}"' | awk '$1 > 5120'

# 5. 确认没有二进制或生成物混入
git diff --cached --numstat | awk '$1 == "-" || $2 == "-" {print}'
```

任一项不符合预期就停止提交，先修正暂存区。**不要用 `git commit --no-verify` 跳过检查，也不要用 `git add -f` 绕过忽略规则。**
