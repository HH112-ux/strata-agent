## 3. 处置步骤

### P0-a 疑似密钥或敏感数据外泄

1. **止血**（目标 1 分钟）
   - 若涉模型服务 Key：立即在火山方舟控制台轮换该 Key（唯一真实止血手段，改代码来不及）。
   - 移除 `.env` 与本机环境变量中的旧 Key。
   - 若涉已推送 commit：按 `docs/conventions/repo-hygiene.md` §2 处置，历史改写不是首选。
2. **取证**
   - 记录泄露时间、渠道（本机 / 已推送 / 日志 / 截图）。
   - 检查 git log 与 reflog，确认是否进入任何分支或 PR。
3. **修复**
   - 轮换后把 Key 引用改为环境变量占位，补 `.env.example`（T012/T019）。
   - 按 repo-hygiene.md 增加 / 触发密钥扫描（gitleaks 接入步骤见该文档 §5）。
4. **恢复**
   - 确认新 Key 生效后恢复演示与测试。
5. **复盘**（24 小时内）
   - 出时间线；必须回答"缺哪份制品导致没早发现"（预期答案：D9 数据边界 + CI 密钥扫描）。

### P0-b 对外写操作误执行（预期场景：未来接入外部工具后）

1. 关对应工具开关（`tool.<name>.enabled`，D8 三级开关之一）。
2. 拉出受影响记录（按 trace 的 `tool.args` 摘要与下游流水对账）。
3. 记录误执行清单与补偿方案，补一条 `evals/regression.jsonl` 用例。
4. 复盘时确认 `capability-contract.yaml` 的 `requires_approval` 是否该置 true。

### P1 核心能力不可用（模型服务挂 / 平台起不来）

1. 判断模型侧还是平台侧：模型服务不可用 → 设 `strata.model.provider=stub` 恢复演示链路（AC-1.4）。
2. 平台侧：`docker compose ps` 检查 PostgreSQL / Redis 健康；按 plan §6 回滚数据变更。
3. 恢复后跑冒烟测试（`scripts/demo.sh`，未实现）确认链路。
4. 若因代码缺陷：`git revert` 对应 commit（禁止 reset，AGENTS.md F3），重新过 PR 审查。

### P2 部分示例 / 场景受影响

1. 确认影响面（按任务 ID 与场景过滤 trace；trace 未实现，先按日志时间窗查）。
2. 若集中在单一工具或数据源，按 P1 处置。
3. 若为模型行为退化，按 `releases.yaml` 的 `rollback_to` 回滚（当前无发布记录，无可用回滚目标）。
